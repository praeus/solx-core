Decision: defer the grant/approval gate. solx-core currently has no allowlist or confirmation step at all for Command/Webhook actions — anything posted to the actions DB is immediately executable. Old sol deliberately required a human-approved grant step precisely to prevent a package from silently self-granting shell/HTTP execution. For now, we're accepting "posted to the DB = trusted" as the working model, to avoid adding permission-system complexity while solx-core itself is still being built out — everything running through it today is trusted by construction. Captured as future hardening work, not blocking the packages effort:

Package signing and verification at install time — so install-package can refuse to run scripts/register actions from a package whose signature doesn't check out, rather than trusting any local directory unconditionally.
A separate permissions module gated on caller identity — flagged as difficult/extensive since it requires solx-core to know who (which human/model/action) is invoking a given action, which the current design doesn't track at all today.
File-operation sandboxing to the files directory — already true today (solx-files rejects path traversal, ../absolute paths — confirmed in the design doc's storage section), noted here as a control that's already in place and should stay true as the rest of this hardening is built out.
Secrets masking in action config — action configs can embed encryption keys/credentials; these should be masked/redacted when read back by anything other than the action that owns them, so one action can't read another's secret out of shared config.
