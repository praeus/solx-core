Decision: defer the grant/approval gate. solx-core has no allowlist or confirmation step for *executing* Command/Webhook actions — anything posted to the actions DB is immediately executable. **Creating** one is now restricted, though: `entity_post_action`/`entity_delete_action` refuse to create, modify, or delete `command` and `webhook` actions. That built-in is the only route to `ActionManager::post` available to an MCP client, a WASM guest, or a `.solx` script (MCP has no separate CRUD layer), so a model or a package's WASM can no longer self-grant shell or outbound HTTP. It also checks the *stored* row, not just the incoming payload, because `post` is a merge-upsert — a payload carrying only `fn_name` would otherwise silently repoint an existing Command action. The CLI reaches `post` directly and is unaffected, which is what package installs rely on. Deliberately not enforced on the HTTP `/actions/post` route: it would break the CLI in remote mode, and anyone holding `server_token` can already exec Command actions, so it would buy nothing. Old sol deliberately required a human-approved grant step precisely to prevent a package from silently self-granting shell/HTTP execution. For now, we're accepting "posted to the DB = trusted" as the working model, to avoid adding permission-system complexity while solx-core itself is still being built out — everything running through it today is trusted by construction. Captured as future hardening work, not blocking the packages effort:

Package signing and verification at install time — so install-package can refuse to run scripts/register actions from a package whose signature doesn't check out, rather than trusting any local directory unconditionally.
A separate permissions module gated on caller identity — flagged as difficult/extensive since it requires solx-core to know who (which human/model/action) is invoking a given action. **Partially addressed.** `solx-actions` now tracks one kind of caller: the action that invoked another action (`caller::Caller`, threaded from `wasm_host` into `LocalActionManager::exec_as`). It exists solely to scope `get_secret`/`set_secret`, and is deliberately contained — the `ActionManager` trait, the HTTP wire format, the CLI, MCP, and `solx-client` are all unchanged, and the caller is never serialized, so it can't be spoofed by a client. External callers (CLI/MCP/HTTP) are still undifferentiated: they are simply "not an action". A general permission system would be a new module and a `Permission` entity type alongside documents/actions/types, mapping a caller to the entities it may access; nothing here presupposes its shape.
File-operation sandboxing to the files directory — already true today (solx-files rejects path traversal, ../absolute paths — confirmed in the design doc's storage section), noted here as a control that's already in place and should stay true as the rest of this hardening is built out.
Secrets masking in action config — action configs can embed encryption keys/credentials; these should be masked/redacted when read back by anything other than the action that owns them, so one action can't read another's secret out of shared config. **Done** (`solx-actions/src/mask.rs`). `ActionManager::get`/`list` redact `action_config.secrets` and `action_config.auth`, so keys never cross the HTTP boundary or reach an MCP client; execution reads through `get_unmasked` and still sees the real values. `post` runs the inverse (`unmask_merge`), restoring anything echoed back as `"***"` from the stored row — so the natural fetch → edit → write-back cycle can't silently destroy a key. An action reaches its *own* key only via `get_secret`/`set_secret`, which resolve against the calling action's `action_config.secrets` and return the decrypted value, never the key.
